# `hidden_field` の役割とセキュリティに関する考察   260906

## 1. `hidden_field` が不要な情報と必要な情報

### 不要な情報
- **予約者名、店舗名、座席情報など**
- **理由:** これらはサーバー側で、より信頼性の高い情報源（`current_user` や URLの `:id`）から再取得できる。ビューでの表示は、あくまでユーザーに見せるためのもの。

### 必要な情報
- **予約時間、電話番号、人数、備考など**
- **理由:** これらはユーザーがフォームで入力した、データベースにまだ存在しない「生」のデータ。画面遷移（フォーム → 確認画面 → 作成処理）の際に情報を引き継ぐために `hidden_field` を使って運ぶ必要がある。これはHTTPリクエストボディにデータを含めるのと同じ役割を持つ。

---

## 2. `hidden_field` は本当に "hidden" なのか？

> けど、hidden_field は外からでも操作できてしまうそうじゃないか。
> 何がhiddenなんだ？

この疑問は非常に重要です。

結論から言うと、`hidden_field` の "hidden" は、**「ユーザーの画面に表示されない」**という意味しかありません。

ブラウザの開発者ツールを使えば、誰でもその存在を確認し、値を読み取り、**書き換えて送信することさえ可能**です。セキュリティ的に「隠されている」わけでは全くありません。

---

## 3. なぜ書き換え可能なのに使うのか？ → 多層防御の考え方

`hidden_field` で送られてきた値をそのまま信用するのは非常に危険です。だからこそ、**サーバーサイドでのバリデーションが最後の砦**として機能します。

- **第一の壁（フロントエンド）:** `hidden_field` で正しい値を引き継ぐ。これは善良なユーザーの操作を助けるため。
- **最終防衛ライン（バックエンド）:** たとえ `hidden_field` の値が改ざんされても、モデル層の `validates` が不正なデータをブロックする。

このアプリケーションでも、`validates :phone_number, format: { with: /\A\d{10,11}\z/ }` や、予約の重複を防ぐカスタムバリデーションが、この最終防衛ラインの役割を担っています。

**`hidden_field` は便利な「情報の運び屋」ですが、その荷物の中身は必ずサーバー側で検問（バリデーション）する**、という原則が極めて重要です。
