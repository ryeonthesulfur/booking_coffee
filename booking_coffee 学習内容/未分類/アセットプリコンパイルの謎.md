# 解説：本番環境と「アセットプリコンパイル」の謎

「`git pull`でコードを更新したのに、CSSが見つからないとエラーが出た…」。
この現象、非常に混乱しますよね。これは、Railsが**「開発環境」**と**「本番環境」**で、CSSやJavaScript（これらを総称して**アセット**と呼びます）の扱い方を全く変えているために起こります。

この謎を解く鍵は、**「レストランの厨房」**にあります。

一番シンプルに言うと:
「本番サーバーでCSSを使えるようにするには、コードを書き換えるたびに rails assets:precompile というコマンドを実行する必要がある」

---

## 2つの厨房：「開発環境」と「本番環境」

### 開発環境（あなたのPC）の厨房

-   **スタイル:** 「家庭のキッチン」
-   **動き方:** 注文（ページ表示リクエスト）が入るたびに、冷蔵庫（`app/assets`）から食材（CSSファイル）を一つ一つ取り出し、その場で調理して提供します。
-   **メリット:** 新しいレシピ（CSSの変更）を試すのが簡単。ファイルを保存すればすぐに反映されます。
-   **デメリット:** 毎回冷蔵庫を開け閉めするので、お客さん（ブラウザ）を待たせる時間が長くなります。

### 本番環境（EC2サーバー）の厨房

-   **スタイル:** 「人気レストランのキッチン」
-   **動き方:** お客さんを待たせないよう、営業開始前に徹底的に**「仕込み」**をします。野菜を切り（CSSの圧縮）、ソースを合わせ（ファイルを結合）、すぐに提供できる状態でカウンター（`public/assets`）に並べておきます。
-   **メリット:** 注文が入ったら、カウンターから完成品を出すだけ。提供スピードが非常に速い。
-   **デメリット:** 新しいメニュー（CSSの変更）を追加したら、必ずもう一度**「仕込み」**をやり直さないと、カウンターには並びません。

---

## 「仕込み」こそが `assets:precompile` の正体

本番環境で行う、この**「仕込み」**作業こそが、以下のコマンドです。

```bash
RAILS_ENV=production bundle exec rails assets:precompile
```

このコマンドは、具体的に以下の4つの重要な「仕込み」を行っています。

1.  **圧縮 (Minify):**
    CSSやJSファイルから、不要なスペースや改行、コメントを全て削除し、ファイルサイズを極限まで小さくします。

2.  **結合 (Concatenate):**
    複数のCSSやJSファイルを一つにまとめ、ブラウザがサーバーにファイルを要求する回数を減らします。

3.  **指紋付け (Fingerprinting):**
    ファイル名にハッシュ値（例: `application-a1b2c3d4.css`）を付けます。これにより、CSSを更新した際にブラウザが古いキャッシュを使い続けるのを防ぎます。

4.  **配置 (Copy):**
    上記1〜3の処理を終えた完成品ファイルを、Webサーバーが直接参照できる公開カウンターである **`public/assets`** ディレクトリにコピーします。

---

## なぜ今回エラーが起きたのか？

今回のデプロイ手順を、レストランの厨房に例えてみましょう。

1.  **`git pull` を実行**
    -   これは、シェフ（あなた）が新しいレシピ本（`app/assets`内の新しいCSSファイルや変更）を受け取った状態です。

2.  **`assets:precompile` を実行し忘れた**
    -   これが致命的でした。新しいレシピ本を受け取ったにもかかわらず、**「仕込み」をやり直すのを忘れてしまった**のです。

3.  **Puma（Webサーバー）を再起動**
    -   ウェイター（Puma）は営業を再開しました。

4.  **ブラウザからアクセス**
    -   お客さん（ブラウザ）が、新しいレシピ（`application.html.erb`）に書かれた「`store_floor_common.css`を使った料理」を注文しました。

5.  **エラー発生**
    -   ウェイターは、仕込み済みの料理が並ぶカウンター（`public/assets`）へ料理を取りに行きました。しかし、「仕込み」を忘れたため、そこに「`store_floor_common.css`を使った料理」は**存在しませんでした**。
    -   結果、ウェイターは「料理が見つかりません！（`Asset Not Found`）」とパニックになり、お店は営業停止（500 Internal Server Error）してしまったのです。

---

## 結論

本番環境では、コードを更新する `git pull` とは別に、**アセット（CSS/JS）を本番用に「仕込み」直す `assets:precompile` が、必ずセットで必要**になります。

`git pull`は「レシピの更新」、`assets:precompile`は「そのレシピに基づいた仕込みのやり直し」。

この2つをセットで行うことで、初めて変更が本番環境に正しく反映されるのです。


---

## 補足：「リストへの追加」ではなく「ビルド作業」そのもの

「リストに追加し忘れた」という表現は少しニュアンスが異なります。より正確には、**「新しいCSSファイルを本番用の完成品に変換・コピーするビルド作業自体が、今回のデプロイ手順から漏れていた」**となります。

仕組みはこうです。

```
app/assets/stylesheets/store_floor_common.css  <-- 元のファイル（ソースコード）
        ↓
      ここで「rails assets:precompile」を実行する必要がある
        ↓
public/assets/store_floor_common-a1b2c3d4.css  <-- 本番環境で実際に使われるファイル
```

本番環境のWebサーバー（PumaやNginx）は、`app/assets/`ディレクトリを**一切見ません**。
彼らが見ているのは、仕込み済みの料理が並ぶカウンター、つまり`public/assets/`ディレクトリだけです。

そして、この`public/assets/`ディレクトリは、セキュリティ上の理由から`.gitignore`ファイルによってGitの管理対象から外されています。そのため、`git pull`でコードを更新しても、このディレクトリの中身は一切更新されません。

つまり、今回のエラーは「リストに加え忘れた」のではなく、**「`app/assets/`にあるソースコードを、`public/assets/`にある完成品に変換・コピーするビルド作業を、デプロイ手順の中で実行し忘れていた」**というのが、より正確な原因です。
