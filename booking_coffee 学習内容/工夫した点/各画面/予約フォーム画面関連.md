## 想定質問1：設計思想について

「このフォームは送信するとすぐに予約完了ではなく、一度確認画面に遷移しますよね。なぜこのような設計にしたのですか？」

**質問の意図:**
- ユーザー体験（UX）を考慮した設計ができるか？
- 単に言われたものを作るだけでなく、その機能の「目的」を考えているか？

### なぜ間取り図画面と予約フォームを一緒にしなかったのか

間取り図を選択できることを、登録していないユーザーでもそれだけ見て空席を視覚的にわかりやすい形で探せる斬新さを体験できるようにしておきたかったから。  
設計当初も、一緒にしようか迷いましたが、あえて棲み分けをし、空席状況と間取り図で選択できる使い勝手の良さを体験させ、  
使いたかったら新規登録・ログインして利用してもらおうという判断をしました。そのため、予約フォーム以降はログインしていないと使えないようにしております。

（初のオリジナルアプリの実装で、制作する際にビューファイルを複雑にせず読みやすいようにしたかったという理由もあります。）

## 想定質問2：動的なUIとデータの整合性について

「この『人数』の選択肢ですが、席によって上限が変わりますよね。これはどうやって実現しているのですか？」

seeds.rb にある定員のキャパシティをカラムメソッドに、用意されたダミーデータを引っ張ってくることで実現しています。  
また、ビューコードには、

```ruby
(1..@seat.capacity).map { |n| ["#{n}名", n] },
```

というふうに記述したことで、取得したダミーデータの定員数が最大値となるようにしています。  
これにより選択した座席タイプの定員数がそのままプルダウンで選択できるようにいたしました。

---

### それとプレースホルダーのところも

**想定される質問：**「この `select:invalid` というCSSセレクタは、どういう目的で使っているのですか？また、なぜこの一工夫が重要だと考えますか？」

「はい。これは、人数のプルダウンメニューに『人数を選択してください』のようなプレースホルダー（入力前の案内文）を設けるために使っています。」

「通常のテキスト入力欄は placeholder 属性で簡単に実現できますが、`<select>` タグにはその機能がありません。  
そこで、required 属性と値が空の `<option>` タグを組み合わせることで、未選択の状態を『無効（invalid）』として扱わせています。」

「この `:invalid` セレクタで、その未選択の状態の時だけ文字色を薄いグレーにすることで、  
テキスト入力欄のプレースホルダーと全く同じ見た目と振る舞いを実現しました。」

**なぜ重要か：**

「フォーム全体のUIに一貫性を持たせるためです。入力欄の種類に関わらず、ユーザーが『薄いグレーの文字は、  
これから入力すべき項目だ』と直感的に理解できるようになります。」

## 想定質問3：データの引き継ぎとJavaScriptの再利用について

「前の間取り図画面で選んだ日時が、このフォームに最初から入力されていますね。このデータの引き継ぎは、どのような仕組みで行っていますか？」

**質問の意図:**
- 画面をまたいだデータの受け渡し方法を理解しているか？
- フロントエンド（JS）とバックエンド（Rails）の連携を説明できるか？

これについては、２つのJavaScriptファイルで対応しております。  
前の間取り図画面にて、予約を進めるボタンをクリックした際に、「toReservation_form.js」がクリックをイベント発火として、  
選択された座席と店舗id、予約日時 をURLに挿入してルーティングに渡して画面遷移します。

遷移後、もう一つのJSファイル「seats_index.js」にて、URLからクエリパラメーターを読み取った日時を  
flatpickr の初期値（defaultDateVal）に設定することで表示しております。

```javascript
const urlParams = new URLSearchParams(window.location.search);
const startTimeParam = urlParams.get('start_time');
```

## readonly: true について ── 手打ち入力の防止

これは、そのテキスト入力欄を**「読み取り専用」**にするための設定です。

### これが何をしているか？

`readonly: true` を指定すると、生成されるHTMLの `<input>` タグに readonly 属性が追加されます。

```html
<input readonly="readonly" class="form-input" type="text" name="reservation[start_time]" id="reservation-date-input">
```

これにより、ユーザーはキーボードで直接この欄に文字を入力することができなくなります。

### なぜ「読み取り専用」にする必要があるのか？

このアプリケーションでは、予約日時はキーボードで手入力するのではなく、flatpickr というJavaScriptのカレンダーライブラリを使って選択する仕組みになっていますよね。

もしこの欄が編集可能だと、ユーザーが "あさって" や "2024/5/17" のような、システムが想定していない形式で日時を入力してしまう可能性があります。  
そうなると、サーバー側でエラーが発生したり、意図しない日時で予約されたりする原因になります。

`readonly: true` を設定することで、

- ユーザーによる手入力を防ぎ、フォーマットの間違いをなくす。
- 日時の選択方法は flatpickr のカレンダー経由のみに強制する。
- flatpickr が選択した日時はこの欄に表示されるので、ユーザーは自分の選択を確認できる。

というメリットがあります。

ちなみに、似たような属性に `disabled: true` がありますが、こちらは入力欄を無効化するだけでなく、  
フォーム送信時にそのデータがサーバーに送られなくなってしまいます。  
今回は予約日時をサーバーに送る必要があるので、`readonly: true` が最適な選択となります。

## アピールポイント：重複チェックバリデーション

**堅牢な設計思想:** フロントエンドの制御を過信せず、サーバーサイドでも検証する「多層防御」の考え方ができている。

**カスタムバリデーションの実装力:** `validates` だけで表現できない複雑なビジネスルール（3時間制の重複チェック）を、`validate` を使って自作メソッドで実装できる。

**高度なActive Recordクエリ:**
- `where("start_time > ? AND ...")`: 複雑な時間条件をSQLクエリに落とし込める。
- `exists?`: 実際にレコードをメモリに読み込むのではなく、存在するかどうかだけを高速にチェックする、パフォーマンスを意識したメソッド選択ができている。

### 想定される質問と回答例

**質問1：「フロントエンドで予約済みの席は選択できないようにしていますが、なぜモデル側でも重複チェックのバリデーションを入れているのですか？」**

悪意のあるユーザーによる直接的なクエリパラメーターの操作によって、予期せぬ形でデータが登録されてしまうのを防ぐために用意しました。  
最終的に重複した予約が送られてきても、このバリデーションによって弾かれる仕様です。
