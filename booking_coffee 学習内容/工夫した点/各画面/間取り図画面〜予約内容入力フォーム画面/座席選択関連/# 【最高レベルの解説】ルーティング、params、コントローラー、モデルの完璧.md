## 1. データが旅するルート（おさらい）

まず、ユーザーがブラウザで操作してからデータが処理されるまでの大きな流れを確認しましょう。

1.  **ブラウザ (View/JavaScript)**
    -   ユーザーが座席「A-1」を選び、「予約へ進む」ボタンをクリック。
    -   JavaScriptが `store_id` や `seat_number` (`"A-1"`) を使ってURL (`/stores/1/seats/A-1`) を組み立てる。
    -   `window.location.href` によって、そのURLへの **HTTPリクエスト** がRailsサーバーに送信される。

2.  **Railsサーバー**
    -   リクエストを受け取ったサーバーは、まず **ルーティング (Routing)** に「このリクエストをどう処理すべきか？」を問い合わせる。
    -   ルーティングはURLを解析し、**コントローラー (Controller)** の特定のアクションを呼び出す。
    -   コントローラーは必要に応じて **モデル (Model)** にデータの検索や保存を依頼する。
    -   最終的にコントローラーが **ビュー (View)** を使ってHTMLを生成し、ブラウザに返す。

あなたの疑問は、この中の「ルーティング → コントローラー」と「コントローラー → モデル」の繋ぎ目にありますね。ここを深掘りしていきましょう。

## 2. 核心①：ルーティングからコントローラーへ 〜`params`はいつ、どう作られるか〜

> コントローラーに来るのは、まんまURLが来るんだっけ？それとも、ルーティングの時点で店舗IDと座席のデータは仮の箱詰めをされて、コントローラーでparams に箱詰めされ直すんだっけ？

素晴らしい質問です。答えは後者に近いです。

**結論：ルーターがURLを解析して`params`という完成品の箱を作り、それをコントローラーに渡します。**

コントローラーは「詰め直し」はしません。ルーターが完璧に準備してくれた`params`を受け取るだけです。

### 流れを分解してみよう

1.  **リクエスト到着**
    -   Railsサーバーに `GET /stores/1/seats/A-1` というリクエストが届きます。

2.  **ルーターの仕事：解析と`params`の構築**
    -   ルーターは `config/routes.rb` を見て、このURLに一致するルールを探します。
    ```ruby
    # config/routes.rb
    resources :stores do
      resources :seats, only: [] do
        resources :reservations
      end
    end
    # この定義が `GET /stores/:store_id/seats/:seat_id/reservations/new` というパターンにマッチする
    ```
    -   URLがパターンに一致した瞬間、ルーターは2つの重要な仕事をします。
        1.  **行き先を決定する**: 「これは `reservations` コントローラーの `new` アクションの仕事だ」と判断します。
        2.  **`params`ハッシュを構築する**: URLのプレースホルダー部分を機械的に切り取り、ハッシュに詰めます。
            -   `:store_id` の部分 → `"1"` を取り出し `params[:store_id] = "1"`
            -   `:seat_id` の部分 → `"A-1"` を取り出し `params[:seat_id] = "A-1"`
            -   この時点で `params` は `{ "store_id" => "1", "seat_id" => "A-1" }` というRubyのハッシュとして完成しています。

3.  **コントローラーのアクション呼び出し**
    -   ルーターは、完成した `params` ハッシュを持って `ReservationsController` の `new` メソッドを呼び出します。
    -   `new` アクションの中では、最初から `params` という変数でこのハッシュにアクセスできます。

**比喩で理解する：郵便局の仕分け係**
-   **リクエスト(URL)**: 宛名が「東京都 港区 1丁目 A-1番地」と書かれた手紙
-   **ルーター**: 郵便局の超優秀な仕分け係
-   **コントローラー**: 港区担当の配達員

仕分け係（ルーター）は、手紙の宛名を見て「これは予約担当（`ReservationsController`）の仕事だな」と判断します。
そして、ただ手紙を渡すのではなく、付箋に「店舗番号: `1`」「座席番号: `A-1`」と分かりやすく書き出して（`params`を作成）、
手紙に貼り付けてから配達員（コントローラー）に渡します。配達員は、自分で宛名を解読し直す必要はなく、付箋を見るだけで必要な情報が手に入ります。

## 3. 核心②：`params`とモデルの関係 〜なぜ`params`の値でモデルを検索できるのか〜

> reservations コントローラーにて、find_by メソッドによって「@seat」にデータが代入されるけど、params に詰め直してるのに、Seat モデルから探してるってどういうことなんだろうって。

ここが最大のポイントであり、あなたの感覚が最も輝く部分です。

**結論：`params`はモデルとは完全に独立した「ただの情報の入れ物」です。コントローラーがその入れ物から情報を取り出し、モデルに「この情報で探してきて」と依頼しているだけです。**

### `find_by`のコードを解剖する

`ReservationsController` の `new` アクションのこの一行を、コンピューターの気持ちになって読んでみましょう。

```ruby
# app/controllers/reservations_controller.rb
@seat = Seat.find_by(seat_number: params[:seat_id], store_id: params[:store_id])
```

このコードは、以下のステップで実行されます。

1.  **`params[:seat_id]` の評価**: `params` ハッシュから `:seat_id` の値 (`"A-1"`) を取り出します。
2.  **`params[:store_id]` の評価**: `params` ハッシュから `:store_id` の値 (`"1"`) を取り出します。
3.  **`Seat.find_by` の呼び出し**: ステップ1と2の結果を使い、実質的に `Seat.find_by(seat_number: "A-1", store_id: "1")` を実行します。
4.  **モデルの仕事（データベースとの対話）**: `Seat` モデルが、この命令を受けて初めてデータベースと対話し、`SELECT * FROM seats WHERE seat_number = 'A-1' AND store_id = 1 ...` のようなSQLクエリを生成・実行します。
5.  **結果の代入**: データベースから返ってきたレコードを元に、`Seat` オブジェクトを生成し、`@seat` 変数に代入します。

### あなたの感覚の正しさ
-   「`params` に詰め込まれてる時点って、まだモデルに行ってない」→ **その通り！** `params`はコントローラーが受け取っただけの、ただのハッシュです。
-   「`params` って、モデル通じて、テーブルに保存されてるわけでもないよね？」→ **その通り！** `params`はリクエストから作られた一時的なデータです。データベースとは何の関係もありません。

`find_by` や `new`, `create`, `update` といった**モデルのメソッドを呼び出す**ことで、初めてコントローラーは `params` の中身をモデルに渡し、データベースとの連携が始まるのです。

**比喩で理解する：レシピと料理人**
-   **`params`**: お母さんから渡された「買い物リスト」と「レシピ」が書かれたメモ
-   **コントローラー**: あなた（料理人）
-   **モデル**: スーパーの店員さんや、キッチンの調理器具
-   **データベース**: スーパーの棚や、冷蔵庫

あなた（コントローラー）は、メモ（`params`）を受け取ります。メモ自体はただの紙切れです。次に、あなたはそのメモを見て、スーパーの店員さん（`find_by`）に「このリストにある『A-1』っていうブランドの牛肉と、『1』番の棚にあるタマネギを探してください」とお願いします。メモが勝手に商品棚（データベース）を探しに行くことは絶対にありません。あくまで、あなた（コントローラー）がメモを読んで、店員さん（モデル）に指示を出すのです。

## まとめ

-   **ルーティング**: URLを解析して`params`ハッシュを作り、適切なコントローラーのアクションを呼び出す「司令塔」。
-   **`params`**: ルーティングが作った、URLやフォームからのデータが入った単なる「Rubyのハッシュ（情報の入れ物）」。
-   **コントローラー**: `params`を受け取り、その中のデータを使ってモデルに命令を出す「現場監督」。
-   **モデル**: コントローラーからの命令を受けて、データベースとやり取りする「実務担当者」。

あなたの疑問は、この役割分担の境界線を正確に捉えようとする、非常にレベルの高いものでした。この理解があれば、今後のRails開発でエラーが発生した際にも、どこに問題があるのかを的確に切り分けられるようになります。
