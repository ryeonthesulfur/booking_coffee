resources :seats, only: [] do   # どの座席の予約内容かをURLで渡すためだけに記述。


なんでここ何もないのにルーティングしてるの？

それは座席の id に係るデータをURLに挿入するためです。

トップ画面と座席選択の間取り図画面にて、Store モデルと紐づいている stores コントローラー経由で表示される情報から
座席に関するデータを reservations コントローラーに渡してその先のビューで表示させる必要があります。

当初、seats コントローラーを用意し、それと紐づいたビューを座席選択の間取り図画面という形で制作していましたが、
リファクタリングの過程で取り止め、stores のアクションで管理することに変更いたしました。

背景には、まず変更前の時点で stores のアクションで管理していたビューは一つだけだったことと、
また、seats のアクションにおいても、管理していたのは間取り図画面だけであったことが挙げられます。

しかし直接的な要因としては、実態は店舗の詳細表示なので、２つもコントローラーを使う必要はなく stores#show で管理するのが自然だと思ったためです。

他方、ユーザーに間取り図で座席をダイレクトに選択できる斬新さを体験してもらいたく、予約入力フォーム画面との差別化も図りたかったこともあり、
reservations#new に合併する判断はあえてやめました。

であればそもそも、seats テーブルで管理しているカラムを  stores か reservations テーブルのいずれかに分配して仕舞えば良かったのではないかと思ったのですが、
今回の予約システムの主人公はあくまで座席なので、裏側のデータベースにおいても、そこは独立して管理したいと思い、判断には至りませんでした。

そこで、座席選択の間取り図画面は stores の詳細アクションで、店舗詳細という体にして管理することにしました。
そのため、この時点で seats テーブルにあるカラムは stores と reservations の各アクションにおいて、橋渡しされるための URL 生成という役割に落ち着きました。


          collection do
            post "confirm"
          end
          member do
            get "complete"
          end


【なぜ予約確認画面へのルーティングネストには、collection と post メソッドを使ったのか】

それぞれ、reservations という集合に対して行うアクションと、保存済みの特定の予約データに対して行うアクションを分けるためです。

予約確認画面というのは、まだDB保存する前なので、予約 id （reservation_id）が存在していません。
また、保存前の予約情報を reservations という集合に対して、これから一つデータを作りますよ」という文脈です。
予約フォーム画面から送られてきた情報は、リクエストボディに載せて送信するため、
HTTPメソッドは、作成を意味する「POST」を使います。

ルーティングは `POST /stores/:store_id/seats/:seat_id/reservations/confirm` というURLを生成します。
このルートは 「`reservations` というリソースグループに属するアクションですよ」とRailsに教えて
親子関係をURLで表現するための書き方です。


一方で、予約の確定については、form_with に入れられた確定内容が、create アクションに送られて保存されます。
そうすると、「redirect_to」メソッドによって完了画面へ遷移します。

この時点で予約データは保存済みのため、完了画面に遷移する際は「特定の予約」に対するアクションなので、IDが必要なmemberを使います。

URLは /stores/:store_id/seats/:seat_id/reservations/:id/complete となります。






【confirm アクションのHTTPメソッドに「POST」を採用した理由】

・HTTPメソッドをGETでリクエストすると、入力した全ての予約情報がURLの末尾にクエリパラメータとしてくっついて送られてしまい、ブラウザ履歴にも情報が残ってセキュリティ上安全ではないため。
・保存用のリクエストボディにあえて予約情報を隠して入れることで、URLに晒すことなく確実に確認画面へ「@reservation」を通じて表示させるため。
