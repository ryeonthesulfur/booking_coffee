## 2026年6月25日 AWSデプロイ手順

今回はコード変更だけでなく、マイグレーション（end_time・total_price削除）も入っているので、以前の手順に「git pull」と「rails db:migrate」を追加する必要があります。

```bash
# AWSコンソールでEC2を起動、新しいパブリックIPを確認
# SSH接続
ssh -i ~/.ssh/booking-coffee-key.pem ubuntu@35.77.101.57

cd booking_coffee
git pull
RAILS_ENV=production bundle exec rails db:migrate
# 「RAILS_ENV=production」は、本番用環境のDB設定を使ってくださいというRailsへの命令。

# Pumaを再起動（既存のプロセスを止めてから）
RAILS_ENV=production bundle exec puma -C config/puma.rb

# 動いているPumaのプロセスID（PID）を確認
ps aux | grep puma
```

**コマンドの解説**

- `ps aux`：今サーバー上で動いている全プロセスを一覧表示する
- `|`（パイプ）：左側のコマンドの出力結果を、右側のコマンドに渡す
- `grep puma`：渡された一覧の中から「puma」という文字列を含む行だけを抜き出す

これを実行する理由は、「今動いているPumaのプロセスのID（PID）」を確認して、それを一旦停止（kill）してから再起動するためです。  
「プロセス」とは、今そのコンピューター（ここではEC2サーバー）の中で実際に動いているプログラムのことです。

例えば、Pumaを起動すると、その瞬間に「Pumaのプログラムが実行中」という状態がコンピューターの中にでき上がります。  
これが1つの「プロセス」です。各プロセスには番号（PID：プロセスID）が振られていて、  
それを使って「このプログラムを止めてください」のような操作ができます。

今回の文脈で言うと、「予約システムのWebサーバーとして動いているPumaというプログラムが、  
今EC2の中で実行され続けている状態」のことを指しています。  
これを一旦止めて、新しいコード（さっき git pull した分）を反映させた状態で再度起動し直す必要があるので、  
まず「今動いているPumaのプロセスを見つける」という作業をしています。

### `RAILS_ENV=production bundle exec puma -C config/puma.rb` の意味

| 部分 | 意味 |
|---|---|
| `RAILS_ENV=production` | 「本番環境の設定を使って」という指定 |
| `bundle exec` | Gemfileに書かれたこのプロジェクト専用のバージョンのgemを使って実行する |
| `puma` | PumaというWebサーバーソフトを起動するコマンド |
| `-C config/puma.rb` | `config/puma.rb` という設定ファイルの内容を読み込んで起動する |

## 15分自動キャンセル実装方式の比較検討

### ① Railsのバックグラウンドジョブ（Active Job + Sidekiq等）

予約作成時に「15分後に自動キャンセル」するジョブをスケジュールする方法。本格的だが、Sidekiqなどのgemとredisのセットアップが必要で、EC2デプロイ時に追加の設定が必要になる。

**全体工程：**

1. Gemの追加：sidekiq（バックグラウンドジョブ管理）と redis（sidekiqが使うデータストア）をGemfileに追加
2. Redisのセットアップ：ローカルにRedisをインストールして起動
3. Active Jobの設定：`config/application.rb` でキューのアダプターをSidekiqに設定
4. Jobクラスの作成：`CancelReservationJob` を作成し、「予約のstatusをcancelledに変える」処理を書く
5. 予約作成時にJobをスケジュール：`create` アクションで予約保存後に「15分後にJobを実行」と登録
6. ローカルで動作確認：Railsサーバーとは別に、Sidekiqのプロセスを起動（ターミナルを2つ使う）
7. **EC2へのデプロイ対応（一番大変）：** EC2にRedisをインストール、Sidekiqを常時起動するサービスとして設定（systemd）、デプロイのたびにSidekiqを再起動する仕組みが必要

---

### ② cronジョブやRakeタスクで定期チェック

定期的に「予約時刻から15分過ぎていて未入店の予約」を探してキャンセルする方法。シンプルだが、チェックの頻度に依存するので最大で数分のズレが出る可能性がある。

**全体工程（Whenever gem + Rakeタスク）：**

1. Gemの追加：`whenever` gem をGemfileに追加（Redisは不要）
2. Rakeタスクの作成：対象予約を探してキャンセルにする処理を書く
3. Wheneverでスケジュール設定：`config/schedule.rb` に「このRakeタスクを毎分実行する」と書く
4. ローカルで動作確認：Rakeタスクを手動実行
5. EC2へのデプロイ対応：`whenever --update-crontab` コマンドを実行するだけ

**①との比較：**

| 項目 | ① Sidekiq | ② Whenever |
|---|---|---|
| 追加gem | sidekiq + redis | whenever のみ |
| EC2設定 | 複雑（systemd等） | コマンド1つ |
| 精度 | 秒単位で正確 | 最大1分のズレ |
| 難易度 | 高い | 低い |

「15分以内に入店しないとキャンセル」は1分のズレがあっても実用上ほぼ問題ないので、ポートフォリオ用途なら②で十分。

## 予約した座席を間取り図から選択できなくなる仕様：作業の流れ

1. `stores#show` で予約済み座席番号の一覧を取得し `@reserved_seat_numbers` に入れる
2. 各間取り図パーシャル（rondo / musubi / kuramae）で、座席ごとに `@reserved_seat_numbers.include?('A-1')` をチェックし `disabled` を付与する
3. CSS で disabled 座席のスタイルを設定する（予約済みの見た目）

`@reserved_seat_numbers` は「ユーザーが選んだ座席」を取得するのではなく、「すでに誰かに予約されている座席番号の一覧」をDBから取得するものです。

**流れ：**

1. ユーザーが店舗詳細ページ（間取り図）を開く
2. `stores#show` がDBから「予約済みの座席番号一覧」を取得
3. 間取り図に反映して、予約済み座席を選択不可にして表示する
4. ユーザーは空いている座席だけ選べる

```ruby
.joins(:seat)
# reservations テーブルと seats テーブルをSQLのJOINで結合する。
# これにより seats のカラムをクエリ内で参照できるようになる。

.pluck("seats.seat_number")
# seats.seat_number の値だけを配列で取得する。
# ActiveRecordオブジェクトを生成せず必要な値だけ取るので軽量。
# 結果は ["A-1", "B-2", "C-3"] のような配列になる。
```
