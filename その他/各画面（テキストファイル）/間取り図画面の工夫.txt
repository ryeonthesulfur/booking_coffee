・「confirm_mode」というローカル変数を作成した。

・なぜそうしたのか

2. 各店舗の間取り図に「content_for」で直接CSS割り当て...
各店舗に用意した間取り図のレイアウトをそれぞれ対応させるために直接このように記述することでCSSを割り当てました。

・なぜそうしたのか
本番環境では、Railsは「application.html.erb」に記述してある「スタメンCSS」を全部まとめて一つの巨大なCSSファイルに結合・圧縮します。
ユーザーが最初にサイトを訪れたとき、この一つのファイルをダウンロードすれば、サイト内のどのページに移動しても、
共通部分のスタイルはすでに手元にある状態になります。
そして、特定のページを開いたときにのみ用いるCSSに関してはその時だけ読み込ませることで、全体の画面遷移でかかる処理の負担を軽くするためです。
これにより、ページ遷移が非常に高速になるからです。

3. 予約済み座席の動的な無効化（ダブルブッキング防止）
実装前は、予約しても、予約済みの座席が再度選択できてしまう状況でした。
これを解決するために、ユーザーが選択した日時に、すでに予約されている座席をリアルタイムで選択不可にする機能を実装しました。


**【実装の流れ】**
1.  **コントローラー（Backend）:** `stores_controller`で、ユーザーが選択した日時を基準に、前後３時間の範囲で利用時間が重複する予約をデータベースから検索します。
                                    そして、その座席番号の配列を`@reserved_seat_numbers`というインスタンス変数に格納します。

2.  **ビュー（Frontend）:** 間取り図のビュー側では、その座席番号がコントローラーから渡された`@reserved_seat_numbers`配列に**含まれているか（`.include?`）**をチェックします。

3.  **動的な表示切替:** もし含まれていれば、条件分岐の（`<%= 'disabled' if reserved %>`）を使い、HTMLの`<label>`タグと`<input>`タグにそれぞれグレイアウトさせます。

この一連の流れにより、ユーザーは直感的に空席状況を把握でき、システムとしても予約の重複を確実に防げるようになりました。


この一連の作業の過程で、日時に関係なく予約済みの座席はグレイアウトされてしまうエラーに遭遇しました。
これでは、間取り図の全ての座席が日時に関係なく埋まってしまった場合、それ以上画面からユーザーが座席を選択することは不可能になってしまいます。
そのため、先述した予約日時（start_time）の３時間前後の範囲という検索条件をwhere句で追加いたしました。

     .where("reservations.start_time > ? AND reservations.start_time <= ?", start_time - 3.hours, start_time + 3.hours)

これにより、指定した予約当日の前後３時間の予約済み座席のみがグレイアウトで表示されるようになりました。

4. 予約日時カレンダー機能を実装したこと
日時カレンダー「flatpickr」を用いて、ユーザーの予約したい日時を選択できるようにした。

ユーザーが任意の予約日時を正しく選択できるようにするためには、
現在時刻以後の日時だけを選択して次の予約フォームの画面に渡すようにしなければならない課題がありました。

これを解決するためには、主に３つアプローチで解決いたしました。

現在時刻と照らし合わせた正しい時刻の選択範囲、
画面リロードの際にURLに予約日時を挿入すること、
次の予約フォーム画面に選択した日時をURLで渡すことです。

まず、間取り図画面に遷移直後は、現在時刻から次の30分間を表示するようにしました。
30分間隔にすることで、店舗側の対応に余裕を持たせることを想定してみたからです。

それから、過去の時刻が選択できないようにし、
選択後のURLリロードの場合は、現在時刻以後であるならそれを反映し、仮に過去の時刻がURLで送られた場合でも現在時刻より次の30分間になるようにしました。
そして、今日中の現在時刻以後の予約も可能にするため、「isDefaultToday」で判定し、「minTime」で時刻選択の可能範囲を決めました。

ここで直面した問題が、一度翌日以降を選択して画面リロードした際に、カレンダー内で今日の日付に戻すと、
その時点で現在時刻より過去であった場合、そのまま予約をすすめられてしまう状態になっていたことです。

したがって、カレンダー内での選択中も、上述した判定と同様に、日付をクリックするたび、今日と照らし合わせる処理を備え付けて、この問題を解決いたしました。
予約日時選択後は、カレンダーを閉じることでリロードされるようにしました。

「flatpickr」とここでの処理は次の予約フォームでも共有されており、選択後のURLがそのまま

    const urlParams = new URLSearchParams(window.location.search);
    const startTimeParam = urlParams.get('start_time');

のコードで引き継がれるようにしました。

このようにして、現在時刻とURLの橋渡しを軸に課題を解決しました。

5. 画面遷移の際にJavaScript を用いたこと...
ユーザーが座席番号を選択した状態で予約をスムーズに進めるため、画面遷移にJavaScriptを用いました。

「予約を進めるボタン」をクリックして、「data-store-id="<%= @store.id %>"
」で店舗id と、ユーザーが選択した座席番号のデータをJavaScriptファイル（toReservation_form.js）で受け取り、
URLに挿入し、「window.location.href」でルーティングに渡して遷移するようにしました。

質問1：「なぜここは、通常の<form>で送信するのではなく、JavaScriptでURLを組み立てて遷移させる方法を選んだのですか？」
質問の意図:

複数の実装方法を知っているか？
なぜその技術を選択したのか、論理的に説明できるか？
RESTfulなURL設計への理解があるか？

回答のポイント:
「はい。最終的に遷移したいURLが /stores/(店舗ID)/seats/(座席ID)/reservations/new という綺麗な形だったためです。」
「通常の<form>でGET送信すると、URLが .../new?seat_id=C-1 のようなクエリパラメータ形式になってしまいます。
今回は、どのリソース（座席）に対する新規作成なのかをURLのパス自体で表現したかったため、JavaScriptで動的にURLを組み立てる方法が最適だと判断しました。」
「この方法により、Railsのルーティングの思想に沿った、RESTfulな設計を維持できると考えました。」

    自分の回答：
そのほうがクエリパラメータ形式よりも可読性が高く感じたからです。また、座席を選択した状態で画面遷移する場合、通常の「link_to」メソッドが使えず、
データを保持して遷移する必要があったからです。

質問2：「このコードで、もしユーザーが座席を一つも選択せずにボタンを押した場合、何が起こるか分かりますか？ それを防ぐにはどうしますか？」

質問の意図:
ユーザーの予期せぬ操作（エラーケース）を想定できているか？
JavaScriptのエラーハンドリングに関する知識があるか？
堅牢なコードを書く意識があるか？

回答のポイント:
（何が起こるか）
「はい、現状のコードですと document.querySelector('input[name="seat_id"]:checked') が null を返すため、
その後の .value を参照しようとした瞬間にJavaScriptエラーが発生し、画面が遷移せず何も起きない状態になってしまいます。」

（どう防ぐか）
「対策として、seatNumber を取得する前に、まず選択された要素（checkedRadio）が存在するかをチェックします。」
「もし存在しなければ、alert('座席を選択してください。') のようなメッセージをユーザーに表示し、return で処理を中断させることで、エラーの発生を防ぎ、ユーザーにも何をすべきか伝えることができます。」

回答例
「はい、現状のコードですと、座席が未選択の状態でボタンを押すと、JavaScriptでエラーが発生し、ユーザーから見ると何も反応がない状態になってしまいます。」
「これは改善点だと認識しており、もし修正するならば、値を取得する前に null チェックを入れ、未選択の場合は『座席を選択してください』といったアラートを表示するように実装します。これにより、ユーザーに次に何をすべきかを明確に伝え、エラーの発生も防ぐことができます。」



自分の回答：
画面遷移せず何も起きません。これは座席番号を格納する変数がnullを返すためです。
