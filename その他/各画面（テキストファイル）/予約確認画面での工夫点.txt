【なぜ hidden_field が重要なのか？】（面接での回答の核）
この確認画面は、ユーザーに予約内容を見せるだけでなく、
「予約を確定する」ボタンが押されたときに、データベースへ保存するための情報をサーバーに送るという、非常に重要な役割を持っています。

1. hidden_field は、そのための**「見えない荷札」**のようなものです。
ユーザーが前の画面で入力した「予約日時」や「人数」といった情報を、この確認画面を経由して、最終的な保存処理（createアクション）へと引き継いでいます。


2. なぜ「予約者名」や「座席番号」は hidden_field にしないのか？ (セキュリティ視点)
ここが最も重要なアピールポイントです。すべての情報をフォームから送るのではなく、
**「サーバー側で、より信頼できる情報源から取得できるデータは、そちらを正とする」**という、Web開発の鉄則を実践しているからです。


予約者名 (user): コントローラー側で current_user を使えば、ログイン中のユーザー情報を安全に取得できます。
店舗 (store) / 座席 (seat): フォームの送信先URL (/stores/1/seats/5/...) にIDが含まれているため、
コントローラーは params[:store_id] や params[:seat_id] を使ってデータベースから正確な情報を取得できます。
もしこれらを hidden_field で送ってしまうと、悪意のあるユーザーがブラウザの開発者ツールで値を書き換え、
「他人になりすまして予約する」「別の高価な席を予約する」といった攻撃が可能になってしまいます。

**サーバー側で取得できる情報はサーバーを信じる。クライアント（ブラウザ）から送られてくる情報は、必要最小限にする。
**この設計思想を語れると、セキュリティ意識の高さを非常に強くアピールできます。



        ＊＊＊面接での想定問答＊＊＊

これは、HTTPリクエストボディにデータを含めるのと同じ役割を持ちます。

あなた: 「はい。この確認画面は、ユーザーに最終確認を促すと同時に、前の画面で入力された予約情報を、次の『作成』処理に引き継ぐ役割を持っています。
            hidden_field は、そのための『見えない荷札』として、ユーザーが入力した予約日時や人数などをサーバーに送信するために使っています。」

hidden_field が要らない予約者名とか店舗名は、元々ダミーデータにあるし、コントローラーから取得してある状態だから必要ない。
これは表示されてるだけ...。

けど、「hidden_field 」が必要な予約時間とか電話番号は、
そもそもカラムだけで、DBに情報はない。これはリクエストボディと同じような役割をしているということか...。



理解が正確です。整理すると:

予約者名・店舗名 → create でも @user = current_user・@store = Store.find(...) でDBから再取得できる → hidden_field 不要、表示だけ
予約時間・電話番号・人数・備考 → ユーザーが入力したデータでDBにまだ無い → hidden_field で運ばないと消える

「何が hidden なんだ」について

おっしゃる通りで、「hidden」は画面に表示されないだけという意味です。
ブラウザの開発者ツールを開けば誰でも見えますし、書き換えて送信することもできます。
セキュリティ上の「隠し」ではなく、ただ「ユーザーの目に触れない入力欄」というだけです。

だからこそ、hidden_field で送られてきた値をそのまま信用してはいけなくて、
サーバー側のバリデーション（モデルの validates）で必ず検証する必要があります。
このアプリでも validates :phone_number, format: { with: /\A\d{10,11}\z/ } などが最終的な防衛線になっています。

【確認画面での間取り図は、どうやって選択した座席を選択した状態で表示させているのか】


確認画面で間取り図に選択した座席を選択された状態で表示したいと思った時、選択した座席のデータを反映させる必要がありました。
そこで、当該の間取り図の全座席分のidを取得し、これをURLを通じてコントローラーが、DBから取得した選択された座席と照らし合わせることで実現しました。
JSでこのコードを記述し、間取り図の全てのラジオボタンを無効化した上、選択した座席のCSSのみを「checked」状態にしました。


 <div id="confirmed-seat" data-seat-number="<%= @seat.seat_number %>"></div>


 仕組みは3ステップです。

①confirm.html.erb が選択した座席番号をHTMLに埋め込む


予約確認画面に移行したら、JSファイルは当該の店舗の間取り図ページから「seat_id」を取得する。
ビューの中にあるこのコードが、@seat の情報（座席番号）（例: A-1）をHTMLの data-seat-number 属性に埋め込みます。


<div id="confirmed-seat" data-seat-number="<%= @seat.seat_number %>"></div>

② `reservation_confirm.js` がそれを読み取ってラジオボタンを操作する
   `document.querySelectorAll('input[name="seat_id"]')` で、まず間取り図上の**全席分のラジオボタン**を取得します。
   そして `forEach` を使って、全席を一つ一つチェックしていきます。
    const seatNumber = selectedSeat.dataset.seatNumber;

    const radios = document.querySelectorAll('input[name="seat_id"]');
    radios.forEach(function(radio) {
        radio.disabled = true; // すべてのラジオボタンを一旦無効化

        // HTMLから取得した座席番号と、今チェックしているラジオボタンのvalueが一致するか確認
        if (radio.value === seatNumber) {
            radio.checked = true; // 該当する座席を選択状態にする
        }
    });

   この処理は、**「全席の中から、目的の席を一つ探し出してハイライトするための総当たりチェック」**を行っています。

.dataset は、data-* という名前の属性にアクセスするための、JavaScriptの決まり文句です。
.seatNumber は、data-seat-number という属性名からハイフンを取り、次の文字を大文字にしたものです（seat-number → seatNumber）。




③confirm_mode: true がフロア表示の調整をする

間取り図パーシャルの中で confirm_mode が true のときは「予約に進むボタン」などを非表示にして、閲覧専用の見た目にしています。

まとめると
「座席番号をHTMLのdata属性に埋め込み → JSがそれを読んでラジオボタンをchecked+disabled状態にする → CSSの :checked スタイルで選択済みに見える」という流れです。


.seat-radio:checked + .seat-box {
  background-color: #78350f;  /* 茶色 */
  border-color: #78350f;
  box-shadow: 0 4px 12px rgba(120, 53, 15, 0.3);
}

JSが radio.checked = true にした瞬間、この :checked 状態に切り替わり、
隣の .seat-box（座席の見た目の箱）が茶色に変わります。+は「直後の兄弟要素」を指すCSSのセレクタです。

つまり「JSが選択状態を作る→CSSが色を変える」という役割分担です。









予約修正　（エラーに直面した）


予約修正の際は、予約フォームで入力した内容を再度表示する必要がありました。
この問題を解決するため、MVCの流れの逆を行えばいいのだと思い、
`confirm.html.erb` の「修正する」リンクに、`@reservation` オブジェクトが持つ情報を渡そうと試みました。

```erb
<%# エラーになるコード %>
<%= link_to "予約内容を修正する", new_store_seat_reservation_path(
  @store,
  @seat.seat_number,
  start_time: @reservation.start_time.strftime("%Y/%m/%d %H:%M〜"),
  @reservation.num_people,
  @reservation.phone_number,
  @reservation.notes
), class: "btn-edit", data: { turbo: false } %>
```

しかし`ActionView::SyntaxErrorInTemplate`という文法エラーに直面しました。

**エラーの原因**: Rubyのメソッド呼び出しのルールでは、**キーワード引数（`key: value` の形式）の後ろに、位置引数（値だけの形式）を置くことはできません。
** 上記コードでは、`start_time:` というキーワード引数の後に `@reservation.num_people` という位置引数が続いているため、文法エラーとなっていました。


このエラーを解決し、正しく情報を引き継ぐには、
Railsの `path_helper`（`xxx_path` という名前のメソッド群）が引数をどのように解釈するかを理解する必要がありました。
そもそもパスヘルパーがとる引数は「位置引数」という各モデルに該当する id が入ります。

今回ならば、
`new_store_seat_reservation_path` が必要とする位置引数は `:store_id` と `:seat_id` の2つだけです。
それ以上の情報を渡したい場合は、「**クエリパラメータ** (`?key=value&...`)」という形式で、すべてキーワード引数にする必要があります。


```erb
<%# 正しいコード %>
<%= link_to "予約内容を修正する", new_store_seat_reservation_path(
  @store,                                     # 1. 位置引数 (routesの :store_id に入る)
  @seat.seat_number,                          # 2. 位置引数 (routesの :seat_id に入る)
  start_time: @reservation.start_time.strftime("%Y/%m/%d %H:%M"), # 3. キーワード引数 (クエリパラメータになる)
  num_people: @reservation.num_people,        # 4. キーワード引数 (クエリパラメータになる)
  phone_number: @reservation.phone_number,    # 5. キーワード引数 (クエリパラメータになる)
  notes: @reservation.notes                   # 6. キーワード引数 (クエリパラメータになる)
), class: "btn-edit", data: { turbo: false } %>
```

また、URLに情報を乗せて渡すだけでは不十分です。
受け取り側である `ReservationsController` の `new` アクションが、その値を読み取ってフォームの初期値として設定する必要があります。

そこで、コントローラーで位置引数の「reservation_params」を使いましたが、ここでもまたエラーになってしまいました。
今回の画面遷移では単純にデータを戻すだけなので、データはネストされておらず「:reservation」キーは紐づけていません。
（データがネストされていない状態っていうのは、単純に予約フォーム画面へのパス「new_store_seat_reservation_path」に直でデータを乗せるって感じです。）

そのため、paramsのなかには「:reservation」が見つからず、エラーとなります。
なので、こうすることで、ルーティングからコントローラーの new アクションに戻った場合、

    @reservation = Reservation.new(params.permit(:start_time, :num_people, :phone_number, :notes)) 　
    
でparamsのハッシュから直接引数にして渡すことで、入力した内容が再表示されるようになりました。

【そのほか】

confirm アクションのHTTPメソッドに「POST」を採用した理由
・HTTPメソッドをGETでリクエストすると、入力した全ての予約情報がURLの末尾にクエリパラメータとしてくっついて送られてしまい、ブラウザ履歴にも情報が残ってセキュリティ上安全ではないため。
・保存用のリクエストボディにあえて予約情報を隠して入れることで、URLに晒すことなく確実に確認画面へ「@reservation」を通じて表示させるため。

確認画面で再度、間取り図を表示する際に選択した座席が選択肢ある状態で表示した理由
・ユーザーが本当にここの座席でいいかもう一度見れるようにするため。
・座席を選択している時の間取り図の画面には、「座席選択」や「ご希望の座席をタップして予約に進んでください。」などの文言があり、確認画面には必要ない情報を表示しないようにするため。

座席予約の間取り図選択画面に「confirm_mode: false」を記述した理由
・パーシャルは、選択するときと確認するときと共有しており、座席予約の間取り図選択画面には上記の文言が表示されるようにするため。

予約時間反映のためのJSファイルに「altFormat オプション」を記述した理由
・dateFormatで「"Y年m月d日 H:i〜"」と記述すると、Rails サーバーは日本語表記の箇所をデータで読み取れないため、表示用のaltFormat オプションを使用。
